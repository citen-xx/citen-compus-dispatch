# 校园信息实验室资源调度与预约系统最终面试稿

## 1. 项目一句话定位

### 1. 极简版
基于 Redis + Lua、Redis Stream、RabbitMQ TTL/DLX 和轻量状态流转的实验室资源预约后端。

### 2. Java 后端版
一个面向实验室预约场景的 Java 后端项目，核心用 Redis + Lua 预扣减、Stream 异步落库、TTL/DLX 补偿和状态流转控制一致性。

### 3. 高并发预约版
围绕高并发预约做的后端链路优化项目，主流程是 Redis + Lua 预扣减、Redis Stream 削峰落库、TTL/DLX 超时补偿和状态流转收口。

### 4. 微服务架构版
一个由 gateway、user-service、order-service 组成的多模块微服务化预约系统，核心用 Redis + Lua、Redis Stream、RabbitMQ TTL/DLX 和状态流转服务保障预约一致性。

### 5. 面试开场版
这个项目本质上是一个实验室资源预约后端，我重点做了 Redis + Lua 预扣减、Redis Stream 异步落库、RabbitMQ TTL/DLX 超时补偿和轻量状态流转收口。

## 2. 简历项目描述最终版

### 1. 保守版
- 基于 Maven 多模块完成 `gateway-service`、`user-service`、`order-service` 的微服务化拆分，统一入口由 Gateway 负责白名单、Redis Token 校验和路由转发，定位清晰、表述稳妥。
- 在预约主链路中使用 Redis + Lua 完成库存判断、用户重复预约判断和 Redis 预扣减，避免请求直接打数据库，真实代码证据充分，限制是当前不是 JWT。
- 使用 Redis Stream 作为真实异步落库主链路，消费成功后才 ACK，失败消息保留在 pending list 重试，限制是当前仍不是完整分布式事务。
- 在消费侧使用 Redisson 用户级锁配合数据库条件更新，避免同一用户并发落库冲突，锁加在 Stream 消费后，不是请求入口幂等锁。
- 使用 RabbitMQ TTL + DLX 做超时补偿，并统一回滚 DB quota、Redis quota 和 Redis 用户预约集合；另外补了确认、取消、超时三条基础状态流转，但不是完整状态机。

### 2. 平衡版
- 将实验室资源预约系统拆成 Gateway、用户服务和订单服务，Gateway 基于 Redis Token 做统一登录态校验和路由转发，解决了后端入口分散的问题，限制是当前不是 JWT 体系。
- 预约请求先走 Redis + Lua，在 Redis 内原子完成 `resource:quota:{resourceId}` 库存校验、`resource:reservation:{resourceId}` 判重和预扣减，再写入 `stream.reservations`，减少高并发下对数据库的直接冲击。
- 把 Redis Stream 作为异步落库削峰主链路，消费侧通过 Redisson 用户级锁和 DB 条件更新串行化处理同用户消息，解决极端并发下重复落库和静默 ACK 风险。
- RabbitMQ 在项目里真实承担的是 TTL + DLX 超时补偿职责：预约创建成功后发送延迟消息，到期后统一收口到超时补偿逻辑，回滚 DB quota、Redis quota 和 Redis 用户预约集合。
- 抽出 `ReservationStatus`、`ReservationStatusEvent` 和轻量 `ReservationStateTransitionService`，集中管理 `PENDING_CONFIRM -> CONFIRMED/CANCELED/TIMEOUT_BREACH` 规则，减少状态判断散落，但仍不是完整状态机框架。

### 3. 高并发后端版
- 以高并发预约为主线，把库存竞争前移到 Redis 层：Lua 原子完成额度判断、重复预约判断、Redis quota 预扣减和 `XADD stream.reservations`，解决数据库第一落点竞争问题。
- 使用 Redis Stream 作为真实异步落库主链路，消费成功后才 ACK，`tryLock` 失败不 ACK，失败消息保留在 pending list；消费侧再用 Redisson 用户级锁和 DB 条件更新保证落库阶段并发安全。
- 订单服务在 `createReservation` 失败时不吞异常，保留消息用于后续重试，同时通过 DB `quota>0` 条件扣减兜底，说明当前实现属于最终一致性设计而不是分布式强事务。
- RabbitMQ 只负责 TTL + DLX 超时补偿，不承担异步落库主链路；超时和主动取消都复用统一资源回滚逻辑，回滚 DB quota、Redis quota 和 Redis 用户预约集合。
- 通过轻量状态流转服务统一确认、取消、超时三条迁移规则，所有更新都依赖 `where status = PENDING_CONFIRM` 的条件更新避免并发覆盖，限制是 `COMPLETE` 仍只是规则预留。

### 4. 冲刺版
- 负责把实验室预约后端拆成 Gateway、user-service、order-service 三个主要运行服务，并用 Gateway + Redis Token 做统一入口校验和路由转发。证据等级 A，风险等级低。
- 设计 Redis + Lua 预约快路径，在 Redis 内原子完成库存校验、判重、预扣减和 Redis Stream 入流，降低高并发预约对数据库的直接冲击。证据等级 A，风险等级低。
- 使用 Redis Stream 作为真实异步落库主链路，消费侧引入 Redisson 用户级锁、成功后 ACK 和 pending list 重试机制，避免锁失败消息静默丢失。证据等级 A，风险等级低。
- 使用 RabbitMQ TTL + DLX 做超时补偿，并把主动取消与超时补偿统一到资源回滚逻辑，回滚 DB quota、Redis quota 和 Redis 用户预约集合。证据等级 A，风险等级低。
- 抽出轻量状态流转服务集中管理 `PENDING_CONFIRM -> CONFIRMED/CANCELED/TIMEOUT_BREACH` 规则，减少状态判断散落；限制是当前不是完整状态机框架，也没有完整完成态闭环。证据等级 B，风险等级中。

## 3. 30 秒 / 1 分钟 / 3 分钟项目介绍稿

### 1. 30 秒版
这个项目是一个实验室资源预约后端，当前是 gateway、user-service、order-service 三个主要服务。预约请求先走 Gateway 校验 Redis Token，然后用 Redis + Lua 做库存预扣减和判重，再把消息写到 Redis Stream 异步落库；消费侧用 Redisson 用户级锁和数据库条件更新保证并发安全，RabbitMQ 的 TTL + DLX 负责超时补偿，确认、取消、超时三条状态流转现在也已经集中收口了。

### 2. 1 分钟版
这个项目我主要把它当成一个高并发预约主链路优化项目来讲。整体上是一个 Maven 多模块微服务化工程，核心服务是 Gateway、用户服务和订单服务。用户请求进来后先经过 Gateway，用 Redis Token 校验登录态，不是 JWT。  
真正的预约快路径在订单服务里：先用 Redis + Lua 在 Redis 内原子做库存判断、重复预约判断和预扣减，同时把预约消息写进 Redis Stream，主线程可以快速返回，不用同步打数据库。后面再由后台消费 Redis Stream 做异步落库，消费侧加 Redisson 用户级锁，结合 DB 条件更新，避免同一用户消息并发落库。  
如果用户长时间不确认，系统会在事务提交后发送 RabbitMQ 延迟消息，TTL 到期后进入死信队列，最终统一走超时补偿，回滚 DB quota、Redis quota 和 Redis 用户预约集合。最近我还把确认、取消、超时三条基础状态流转收口到了一个轻量状态流转服务里，但这还不是完整状态机。

### 3. 3 分钟版
这个项目我一般会从“为什么做”和“主链路怎么跑”两部分讲。业务上它是实验室资源预约场景，问题不是普通 CRUD，而是高并发预约下怎么防止库存被超扣、怎么把落库异步化、怎么做超时回滚。  
架构上当前是一个 Maven 多模块微服务化工程，主要运行服务有 Gateway、user-service 和 order-service。Gateway 做统一入口、白名单、Redis Token 登录态校验和路由转发，所以这里我不会说 JWT。  
真正的预约主链路在 order-service。用户请求先到 `/reservation/reserve/{id}`，服务拿到当前用户后，不是直接访问数据库，而是先执行 Lua 脚本。Lua 会在 Redis 里一次性做三类事情：先判断 `resource:quota:{resourceId}` 是否还有额度，再判断 `resource:reservation:{resourceId}` 里有没有当前用户，最后如果通过，就把 Redis quota 减 1，并把预约消息 `XADD` 到 `stream.reservations`。这样做的好处是把竞争前移到 Redis，主线程可以快速返回。  
后面真正的落库是 Redis Stream 消费线程来做。消费端会先按用户加 Redisson 锁，也就是 `lock:reservation:{userId}`，然后进入事务方法做 DB 二次判重、DB quota 条件扣减和预约记录保存。这里我们还补过一个关键点，就是只有处理成功才 ACK，如果锁没拿到或者落库异常，就不 ACK，让消息留在 pending list 后续重试。  
RabbitMQ 在这个项目里不是异步落库主链路，它的真实职责是 TTL + DLX 超时补偿。预约创建成功提交后会发送延迟消息，到期后进入死信队列，再统一走超时补偿逻辑。补偿逻辑现在已经做了三段回滚：DB quota 回滚、Redis quota 回滚、Redis 用户预约集合 `SREM`。  
在状态上，我最近又补了一层轻量状态流转服务，把确认、取消、超时三条基础迁移集中管理。现在真实能讲的流转是 `PENDING_CONFIRM -> CONFIRMED`、`PENDING_CONFIRM -> CANCELED`、`PENDING_CONFIRM -> TIMEOUT_BREACH`。它不是完整状态机框架，但已经能用规则表加条件更新把并发覆盖问题收住。  
最后还有一条用户感知链路是 WebSocket，当前主要按 `labId` 做预约状态广播，不是用户级精准推送。这也是我会主动说明的边界。

## 5. 核心链路逐条讲解

### 1. Gateway + Redis Token 鉴权链路
一句话概括：所有入口请求先走 Gateway，用 Redis Token 做统一登录态校验。
请求入口 / 触发点：客户端请求 Gateway。
核心类 / 方法：`AuthGlobalFilter.filter()`。
数据如何流转：请求头带 `authorization` -> Gateway 查 Redis 登录态 -> 校验通过后路由转发。
已有代码证据：`citen-gateway`、`AuthGlobalFilter`、Gateway 路由配置。
已验证证据：代码和配置都存在。
当前限制：不是 JWT；下游并没有完整 Feign 透传链路。
面试推荐说法：当前统一入口是真实存在的，但鉴权是 Redis Token，不是 JWT。
面试危险说法：我这里已经做了完整 JWT 鉴权体系。

### 2. 用户预约资源主链路
一句话概括：预约请求先走 Redis 快路径，再走 Stream 消费落库和后续补偿。
请求入口 / 触发点：`POST /reservation/reserve/{id}`。
核心类 / 方法：`ReservationController.reserveResource()`、`ReservationServiceImpl.reserveResource()`。
数据如何流转：Gateway 校验 -> Lua 预扣减和判重 -> XADD Redis Stream -> 消费线程落库 -> afterCommit 发 TTL 消息 -> 后续状态广播。
已有代码证据：控制器、Lua、Stream 消费、`createReservation()`、afterCommit。
已验证证据：源码编译通过。
当前限制：不是完整分布式事务；没有压测报告。
面试推荐说法：高并发竞争前移到 Redis，数据库只承担最终落库。
面试危险说法：我这里每一步都是强一致事务。

### 3. Redis + Lua 预扣减链路
一句话概括：Lua 在 Redis 内原子做库存判断、判重、预扣减和入流。
请求入口 / 触发点：预约接口内执行 Lua。
核心类 / 方法：`seckill.lua`、`StringRedisTemplate.execute()`。
数据如何流转：读 `resource:quota` -> 判 `resource:reservation` -> `quota -1` -> `SADD` -> `XADD stream.reservations`。
已有代码证据：Lua 脚本、`reserveResource()`。
已验证证据：源码存在，构建通过。
当前限制：key 维度还是资源级，不是更细的时段级模型。
面试推荐说法：Lua 解决的是 Redis 层原子性，不是整条链路的最终一致性。
面试危险说法：Lua 一上就彻底解决了所有一致性问题。

### 4. Redis Stream 异步落库链路
一句话概括：Redis Stream 才是当前真实的异步落库削峰主链路。
请求入口 / 触发点：Lua `XADD stream.reservations` 之后。
核心类 / 方法：`ReservationTaskHandler`、`handlePendingList()`、`processReservationRecord()`。
数据如何流转：Stream 写入消息 -> 消费线程读取 -> 成功后 ACK -> 失败保留在 pending list。
已有代码证据：`ReservationServiceImpl` 中的 Stream 读取和 ACK 逻辑。
已验证证据：源码编译通过。
当前限制：没有更复杂的多消费者组治理；没有独立监控面板。
面试推荐说法：RabbitMQ 在项目里不是落库主链路，真实削峰链路是 Redis Stream。
面试危险说法：Redis Stream 和 RabbitMQ 在这里是同一职责。

### 5. Redisson 消费侧用户级锁链路
一句话概括：Redisson 用在 Stream 消费后的落库阶段，按用户维度串行化处理。
请求入口 / 触发点：Stream 消费线程处理预约消息。
核心类 / 方法：`handleReservation()`。
数据如何流转：取 `userId` -> `getLock(lock:reservation:{userId})` -> 成功则落库 -> 失败不 ACK。
已有代码证据：`ReservationServiceImpl.handleReservation()`。
已验证证据：源码编译通过。
当前限制：没有显式 `waitTime/leaseTime` 配置。
面试推荐说法：Lua 和 Redisson 不是重复，Lua解决 Redis 预扣减，Redisson 解决消费落库阶段并发。
面试危险说法：只靠 Redisson 就能防超卖。

### 6. RabbitMQ TTL + DLX 超时补偿链路

## 6. 重点技术点深挖

### 1. Redis + Lua
为什么把竞争前移到 Redis：因为预约场景的第一瓶颈是库存竞争，如果一上来就打数据库，在高并发下会把竞争集中到 DB。把库存判断和判重前移到 Redis，可以把主线程变成一个内存级快路径。
Lua 为什么能保证原子性：因为 Lua 脚本在 Redis 内是单线程执行的，库存判断、判重、扣减、写 Stream 是一次连续执行的，不会被别的命令打断。
quota key 怎么设计：当前是 `resource:quota:{resourceId}`，是资源级额度 key。
reservation set 怎么防重复：当前用 `resource:reservation:{resourceId}` 存用户集合，`SISMEMBER` 判重，`SADD` 记录已预约用户。
为什么 XADD 也放进 Lua：因为这样预扣减和入流能放在一个原子脚本里，避免扣减成功但消息没入流。
Lua 返回码怎么设计：当前可以理解成 `0` 成功、`1` 库存不足、`2` 重复预约，其他视为失败。
Lua 成功但 DB 失败怎么办：当前不 ACK Stream 消息，先靠 pending list 重试；如果 DB 长时间失败，仍不是完整分布式事务，需要后续补偿和人工介入。
当前补偿边界是什么：当前已经能回滚 DB quota、Redis quota 和 Redis 用户预约集合，但没有 outbox、没有全局事务、没有完整自动化补偿中心。

### 2. Redis Stream
为什么真实异步落库主链路是 Redis Stream：因为 Lua 成功后写入的是 `stream.reservations`，真正消费并落库的也是这个 Stream，而不是 RabbitMQ。
Stream 消息体包含什么：当前至少有 `userId`、`resourceId`、`id` 这几个字段，对应预约落库所需的关键标识。
消费者如何读取：`ReservationTaskHandler` 通过 `opsForStream().read(...)` 拉消息，异常时再处理 pending list。
为什么成功后才 ACK：因为只有真正落库成功了，这条消息才算处理完成；否则 ACK 了会丢掉重试机会。
Pending List 有什么作用：当消息已经投递给消费者但没 ACK 时，会进入 pending list，后续可以继续重试。
Redisson tryLock 失败为什么不能 ACK：因为这不代表业务处理完成，只是锁没拿到，如果 ACK 就会把未处理消息静默丢掉。
Redis Stream 和 RabbitMQ 在项目里的职责区别：Redis Stream 负责预约异步落库；RabbitMQ 负责 TTL + DLX 超时补偿。

### 3. Redisson
锁加在哪里：加在 Redis Stream 消费后的落库阶段。
锁 key 怎么设计：`lock:reservation:{userId}`。
为什么是用户级锁：当前主要是为了避免同一用户消息在消费侧被并发落库。
它和 Lua 分别解决什么问题：Lua 解决 Redis 层原子预扣减和判重；Redisson 解决异步消费落库阶段的串行化。
tryLock 失败为什么要保留消息：因为锁失败只是当前竞争失败，不代表消息没价值，保留在 pending list 才有重试机会。
当前没有显式 waitTime / leaseTime 怎么回答：可以实话说当前代码没有显式配置这两个参数，依赖的是默认行为，后续如果进入生产级别会再细化。

### 4. RabbitMQ TTL + DLX
为什么不用定时任务扫表：因为定时扫表会不断打数据库，资源浪费大，而且不够实时。
TTL queue 和 DLX queue 怎么流转：预约创建成功后消息先进入 TTL 队列，到期后通过死信交换机转发到 timeout queue。
超时消息什么时候发送：预约创建成功、事务提交之后发送。
为什么要 afterCommit 发送：因为只有 DB 事务提交成功，超时补偿消息才有意义，否则可能出现消息已发但订单没落库。
超时后为什么用 DB 条件更新：因为要确保只有还处于 `PENDING_CONFIRM` 的预约才会被改成 `TIMEOUT_BREACH`，避免覆盖确认或取消后的状态。
为什么 RabbitMQ 不是异步落库主链路：因为真正异步落库的消息来源、消费逻辑和 ACK 机制都在 Redis Stream 上。

### 5. 状态流转服务
为什么不直接散落 if-else：因为确认、取消、超时都要判断当前状态是否合法，如果规则散在各个方法里，后续很容易不一致。
ReservationStatusEvent 有哪些：`CONFIRM`、`CANCEL`、`TIMEOUT`、`COMPLETE`。
合法流转规则有哪些：`PENDING_CONFIRM -> CONFIRMED/CANCELED/TIMEOUT_BREACH`，以及预留的 `CONFIRMED -> COMPLETED`。
为什么不是完整状态机：因为这里只是规则表加条件更新，没有引入 Spring StateMachine，也没有完整生命周期编排。
条件更新如何避免并发覆盖：因为确认、取消、超时都会带 `where status = PENDING_CONFIRM`，只有一个路径能更新成功。
确认、取消、超时同时发生时怎么保证只有一个成功：靠 DB 条件更新作为最终仲裁层，先更新成功的赢，后来的自然失败。

### 6. 库存回滚一致性
为什么只改 DB 不够：因为预约主链路先改的是 Redis，如果只回滚 DB，不回滚 Redis，会导致缓存和数据库状态不一致。
为什么还要回滚 Redis quota：因为 Redis quota 是预约快路径的库存来源，不回滚会让后续预约继续看到错误库存。
为什么还要 SREM 用户集合：因为 Redis 用户集合承担去重职责，不删会让用户被永久判成“已经预约过”。
取消和超时为什么复用回滚逻辑：因为两者都意味着这次待确认预约失效，资源要释放，回滚对象完全一致。
重复取消为什么不会重复回滚：因为取消前必须先把状态从 `PENDING_CONFIRM` 更新到 `CANCELED`，第二次已经不满足条件了。
当前仍不是完整分布式事务怎么解释：当前已经把补偿边界做实了，但没有全局事务、没有 outbox、没有事务消息表，所以本质还是最终一致性方案。

### 7. Gateway 鉴权
Gateway 做了什么：统一入口、白名单、Redis Token 校验、路由转发。
为什么当前不是 JWT：因为当前代码真实依赖的是 Redis 登录态校验，没有 JWT 解析器和签发逻辑。
Redis Token 怎么校验：通过请求头里的 token 去 Redis 查登录态信息。
下游服务如何拿用户信息：当前 Gateway 可以透传头，但服务内真实使用的是 `RefreshTokenInterceptor + UserHolder`，在请求线程内重新把用户上下文放到 ThreadLocal。
ThreadLocal 只在服务内请求线程使用怎么解释：可以实话说当前没有做完整 Feign 透传，它更多是服务内请求上下文，而不是跨服务上下文框架。

### 8. WebSocket
WebSocket 在项目里做什么：做预约状态变化后的实时广播。
为什么是按 labId 广播：因为当前连接管理是按 `labId` 聚合的，实现简单、业务也能成立。
为什么不能说用户级精准推送：因为当前没有基于用户 ID 的精确会话路由，也没有对应鉴权和映射管理。
状态变化什么时候推送：创建成功后、确认成功后、取消成功后、超时补偿后都会触发状态广播。
当前 WebSocket 有哪些不足：没有用户级精准推送、没有完整鉴权、没有更细的连接治理和消息可靠性保证。

## 8. 风险口径专项

### 1. 不能说 JWT
面试官可能怎么问：你 JWT 放在哪里解析？
错误回答：Gateway 里已经做了 JWT，只是没单独抽工具类。
稳妥回答：当前代码真实做的是 Redis Token 登录态校验，不是 JWT。
更高级的回答：我会把它表述为“统一入口鉴权”，但会明确说具体实现是 Gateway + Redis Token，而不是 JWT。
可以如何转成加分点：强调自己会按代码证据说话，不拿设计稿冒充实现。
简历里应该怎么写：Gateway + Redis Token 登录态校验。
简历里不能怎么写：Gateway + JWT 统一鉴权。

### 2. 不能说 Feign 拦截器
面试官可能怎么问：你的 Feign 拦截器在哪？
错误回答：已经做了，只是没提交。
稳妥回答：当前没有 Feign 拦截器跨服务透传，服务内上下文主要靠 ThreadLocal。
更高级的回答：我会把“跨服务透传”降成“服务内请求上下文管理”，避免夸大。
可以如何转成加分点：说明自己能区分服务内 ThreadLocal 和真正跨服务透传。
简历里应该怎么写：服务内通过拦截器 + ThreadLocal 保存当前用户上下文。
简历里不能怎么写：Feign 拦截器 + ThreadLocal 全链路透传。

### 3. 不能说自定义注解策略工厂
面试官可能怎么问：你的自定义注解在哪？
错误回答：之前做过，后来删了。
稳妥回答：当前项目没有自定义注解策略工厂，只做了轻量状态流转服务。
更高级的回答：我会把抽象重点放在当前真实的状态流转收口，而不是没落地的策略框架。
可以如何转成加分点：说明自己优先做主链路而不是堆模式。
简历里应该怎么写：无。
简历里不能怎么写：自定义注解 + Spring DI 动态策略工厂。

### 4. 不能说完整状态机框架
面试官可能怎么问：你用的是 Spring StateMachine 吗？
错误回答：差不多，思想一样。
稳妥回答：不是，这里只是轻量状态流转服务，没有引入 StateMachine。
更高级的回答：当前状态规模不大，所以我先用规则表 + 条件更新做轻量收口，后续复杂了才考虑完整框架。
可以如何转成加分点：体现取舍能力。

## 11. 最终必背 30 问

关键词：Redis Lua、Stream、Redisson、TTL/DLX、状态流转。
证据：控制器、Lua、Stream、状态服务。
不能说的话：完整中台、JWT、完整状态机。

30 秒回答：是 Maven 多模块微服务化工程，主要运行服务是 gateway、user-service、order-service，但拆分粒度偏粗，不是非常细的服务群。
关键词：三服务、多模块、粒度偏粗。
证据：模块结构。
不能说的话：完整大型分布式中台。

3. 问题：Gateway 在这里做了什么？
30 秒回答：Gateway 做统一入口、白名单、Redis Token 校验和路由转发，当前不是 JWT。
关键词：统一入口、Redis Token、路由。
证据：Gateway 过滤器和路由配置。
不能说的话：JWT 统一鉴权。

4. 问题：为什么当前不是 JWT？
30 秒回答：因为真实代码里没有 JWT 的签发和解析逻辑，当前实现就是 Redis Token 登录态校验。
关键词：代码真实性、Redis Token。
证据：当前实现。
不能说的话：JWT 已实现但没展示。

5. 问题：预约接口怎么抗并发？
30 秒回答：先用 Redis + Lua 做库存判断、判重和预扣减，再写入 Redis Stream 异步落库，消费侧再用 Redisson 和 DB 条件更新做第二层保护。
关键词：Redis 快路径、Stream、Redisson、DB 条件更新。
证据：Lua、消费逻辑。
不能说的话：只靠数据库锁。

6. 问题：为什么用 Redis + Lua？
30 秒回答：因为要把高并发库存竞争前移到 Redis，而且 Lua 能保证库存判断、判重、预扣减和入流在 Redis 内原子执行。
关键词：竞争前移、原子性。
证据：Lua 脚本。
不能说的话：Lua 解决了所有一致性问题。

7. 问题：Lua 脚本具体做了什么？
30 秒回答：判断 `resource:quota` 是否足够、判断 `resource:reservation` 是否已有当前用户、执行 Redis quota 预扣减，并 `XADD` 到 `stream.reservations`。
关键词：quota、set、XADD。
证据：`seckill.lua`。
不能说的话：只是单纯扣库存。

8. 问题：Redis Stream 和 RabbitMQ 分别做什么？
30 秒回答：Redis Stream 是当前真实异步落库主链路，RabbitMQ 负责 TTL + DLX 超时补偿。
关键词：Stream 落库、MQ 补偿。
证据：Stream 消费、MQ 监听。
不能说的话：RabbitMQ 异步落库主链路。

9. 问题：为什么说 RabbitMQ 不是异步落库主链路？
30 秒回答：因为当前真正读取并落库的是 `stream.reservations`，RabbitMQ 监听器只处理超时补偿。
关键词：职责边界。
证据：Stream 消费线程、TimeoutListener。
不能说的话：两个都算主链路。

10. 问题：为什么成功后才 ACK？
30 秒回答：因为只有消息真正落库成功才算处理完成，锁失败或落库异常都不能 ACK，否则会静默丢消息。
关键词：ACK 后移、pending list。
证据：`processReservationRecord`。
不能说的话：ACK 放哪都一样。

11. 问题：pending list 有什么用？
30 秒回答：它用来保留已经投递但还没 ACK 的失败消息，后续可以继续重试，不至于直接丢。
关键词：失败恢复。
证据：`handlePendingList`。
不能说的话：只是日志用。

12. 问题：Redisson 锁加在哪里？
30 秒回答：加在 Redis Stream 消费后的落库阶段，按 `userId` 获取 `lock:reservation:{userId}`。
关键词：消费侧、用户级锁。
证据：`handleReservation`。
不能说的话：入口全局锁。

13. 问题：Redisson 和 Lua 会不会重复？
30 秒回答：不重复，Lua 解决 Redis 层原子预扣减，Redisson 解决消费落库阶段的串行化问题。
关键词：分层职责。
证据：Lua + 锁逻辑。
不能说的话：两者做同一件事。

14. 问题：tryLock 失败为什么不能 ACK？
30 秒回答：因为锁失败只是当前拿不到锁，不代表业务已经处理完成，ACK 了会直接丢掉这条消息。
关键词：未完成不能 ACK。
证据：锁失败抛异常逻辑。
不能说的话：只是为了保险。

15. 问题：超时取消怎么实现？
30 秒回答：预约创建成功后 afterCommit 发 TTL 消息，到期进入 DLX timeout queue，再由监听器调用超时补偿逻辑。
关键词：afterCommit、TTL、DLX。
证据：RabbitMQConfig、TimeoutListener。
不能说的话：定时任务扫表。

16. 问题：为什么要 afterCommit 发超时消息？
30 秒回答：因为只有 DB 事务提交成功后，这条超时补偿消息才有意义，否则会出现消息有了但预约记录没落库。
关键词：事务边界。
证据：afterCommit 发送逻辑。
不能说的话：只是写法习惯。

30 秒回答：因为预约主链路同时改了 DB 和 Redis，如果只回滚一层，就会留下库存或判重脏数据。
